# 真实御魂数据接入设计

## 目标

把桌面端从固定演示库存切换为 MuMu 实机数据。用户在游戏内打开方案详情或御魂详情，助手只读取当前截图，解析后保存到本地 SQLite；配装、评分和强化建议只使用已确认的真实记录。`--demo` 模式仍保留演示数据。

## 约束

- 默认只读，不自动翻页、点击御魂、锁定、弃置、强化或穿戴。
- 不读取游戏进程内存，不抓取或修改网络协议，不注入客户端。
- OCR 置信度低于 `0.92` 的记录允许保存为“待复核”，但不得进入破坏性动作。
- `|TA|...` 是游戏侧方案标识，助手只校验并复制；由游戏导入和计算后，助手从当前方案详情页读取可见约束。
- 每条御魂记录必须有用户指定或 OCR 识别的位置和星级；无法识别套装、等级、主属性时拒绝入库并给出缺失字段。
- 截图、数据库和审计日志只保存在本机 `data/`，不提交到 Git。

## 用户流程

1. 正常模式启动时，仓库为空则显示“尚未采集真实御魂”，不得显示演示御魂。
2. 用户连接 MuMu，在游戏内打开某枚御魂的详情页。
3. 用户在助手中选择位置和星级；套装名可由 OCR 自动识别，也可手动覆盖。
4. 点击“新增读取”。助手截屏、OCR、解析并展示结果，成功后以独立本地 ID 写入 SQLite；相同属性的不同御魂不会相互覆盖。
5. 强化后可选中原记录执行“更新选中”，误识别记录可从本地删除；这些操作都不向游戏发送输入。
6. 在游戏内切换下一枚御魂并重复采集。表格、评分、保护状态和强化候选即时刷新。
7. 对方案码，用户先在助手中校验并复制，再在游戏“阵容助手”中导入、计算并打开方案详情；填写目标式神基础速度后，点击“读取当前游戏方案”提取套装、二四六号位主属性和可见阈值。
8. 助手把面板速度减去式神基础速度，展示识别摘要供确认后，再以真实库存和当前方案约束求六件套；不满足时生成真实胚子的 `+3` 强化建议。首版只给建议，不自动强化。
9. 暴击、攻击、生命、防御、效果命中/抵抗等面板阈值在基础值和套装加成尚未建模前会拒绝应用，不用不完整数据生成“满足”结论。

## 组件

### OCR 解析器

`application/inventory_capture.py` 提供：

- `SoulDetailParser.parse(boxes, slot, rarity, set_name_override)`：把文字框转换为 `Soul`。
- `SchemeRequirementParser.parse(boxes, weights)`：把可见方案约束转换为 `BuildRequirement`。
- 中文属性别名、百分比属性、中文/阿拉伯数字位置、`+0..+15` 等级、锁定和已装备状态标准化。
- 解析器使用标准化字段生成 SHA-256 内容指纹；应用保存时分配独立本地 ID，并通过“更新选中”明确维护同一枚实体记录。

### 应用状态

正常模式从 `AppRepository.list_souls()` 构造状态；演示模式才调用 `create_demo_state()`。每次采集或读取方案后重新运行组合优化和强化排序。

### GUI

- “御魂仓库”新增真实采集栏、状态信息，以及“新增读取”“更新选中”“删除选中记录”按钮。
- “方案配装”明确方案码需由游戏导入，新增“读取当前游戏方案”。
- 总览、仓库、配装和强化页支持刷新状态。
- OCR 在采集期间显示等待光标；解析失败不修改数据库。

## 错误与安全

- 未连接 MuMu、游戏不在前台或不是御魂/方案详情页：显示可执行提示，不写库。
- 缺失字段：列出缺失字段；用户可填写套装名、位置和星级后重试。
- 实体身份：新增读取生成独立本地 ID；强化后通过选中记录明确覆盖，允许属性完全相同的多枚御魂共存。
- OCR 低置信度：表格显示“待复核”，安全策略自动保护。
- 自动战斗仍保留，但风险提示与只读采集分离；真实采集本身不发送任何 ADB 输入。
- 自动任务运行时禁用连接、采集和方案读取；只读 OCR 使用独立快照，不覆盖自动化动作缓存。

## 验收

- 无 MuMu 的单元测试覆盖御魂详情解析、方案约束解析、实体 ID 更新/同属性共存和真实/演示状态切换。
- GUI 冒烟测试验证正常模式不显示演示库存、采集成功后表格刷新、解析失败不写库。
- 全量测试、`compileall`、`pip check` 和 `git diff --check` 通过。
