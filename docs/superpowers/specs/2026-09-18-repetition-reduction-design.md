# 御魂匠重复劳动削减设计

## 产品目标

御魂匠的核心不是“能点游戏”，而是安全地替用户完成可重复、可验证的工作：建立真实御魂库存，理解方案需求，给出可执行的配装与强化计划，并在明确入口下循环日常副本。任何无法验证的动作都停止，而不是猜坐标继续。

本设计覆盖三个可独立交付的子系统：

1. **真实库存**：可靠读取单枚御魂、导入已有 JSON 快照，并逐步演进到引导式批量扫描。
2. **整理与配装**：按方案约束从真实库存求解，无法满足时推荐值得强化的胚子；锁定、弃置、强化和穿戴必须先生成预览计划。
3. **日常循环**：困 28 与御魂副本使用版本化视觉配置和有限状态机，体力不足、背包满、掉线、未知界面或达到上限时停止。

## 已确认的根因

当前“御魂读取”不是完整库存读取器，而是要求用户逐枚打开详情页后读取一次。失败日志显示解析器在入口校验阶段就拒绝画面；它硬性要求 OCR 识别到“御魂详情 / 御魂强化 / 御魂属性”标题，并把 `0.92` 同时用作页面判断和字段可信度。当前游戏详情面板并不保证出现这些标题，风格化字体也会让局部文字低于该阈值，因此即使套装、等级和属性可见也会被误判为错误页面。

此外，旧流程没有保存原始截图和 OCR 框，错误日志只有一句“当前画面不像御魂详情页”，无法区分 ADB 截图、OCR 初始化、页面布局、文字阈值或字段解析中的哪一层失败。日常状态机也有同样问题：出现 `unrecognized_scene` 后没有留下足够的现场证据。

## 安全边界

- 不读取游戏进程内存，不注入客户端，不抓取或修改网络协议，不实现反作弊规避。
- 屏幕采集、OCR 和 JSON 导入是只读操作；数据只保存在本机 `data/`。
- 自动锁定、弃置、强化和穿戴属于写操作，必须经过“识别 → 计划 → 用户确认 → 执行 → 复核”五段流程。
- 低置信度、已装备、已锁定、被方案引用、六星速度胚及高潜力御魂默认永久进入保护集。
- 禁止购买体力、充值、勾玉消费和自动处理登录验证。
- 每个自动任务都有次数与时长硬上限；`F12`、ADB 断开、体力不足、背包满、登录页、网络错误和连续未知场景立即停止。

## 架构

### 1. 观察层

`CaptureBundleService` 对一次只读采集生成本地证据包：

- 原始 PNG；
- 设备序列号、分辨率、采集时间和用途；
- RapidOCR 返回的全部文字、置信度和坐标；
- 解析结果或错误阶段。

证据包位于 `data/diagnostics/<timestamp>-<purpose>/`，不会提交到 Git。UI 提供“打开诊断目录”和简洁的可执行错误提示。日常状态机在未知场景停止时使用同一格式保存最后现场。

### 2. 真实库存接入

保留两条互补路径：

- **屏幕路径（默认）**：用户打开御魂详情，助手只截图。解析器通过“已知套装名或用户覆盖值 + 强化等级 + 属性行的空间聚类”判断详情面板，不依赖不存在的固定标题。结构判断允许较低阈值，字段原始置信度完整保留；关键字段不全仍拒绝入库。
- **文件路径（快速）**：导入用户已有的御魂 JSON 快照。适配器先识别格式，再映射为统一 `Soul` 模型，展示新增、更新、跳过和错误数量，用户确认后一次性写库。助手不内置、下载或调用需要进程注入/账号凭证的导出器。

引导式批量屏幕扫描在采集到实际 UI 证据包后启用：从御魂整理页开始，只执行打开卡片、读取详情、关闭详情和翻页；扫描阶段绝不点击锁定、弃置、强化或穿戴。页面指纹不匹配即停止。

### 3. 方案、配装与强化

`|TA|...` 方案码继续交给游戏导入和计算，因为它是游戏侧不透明标识。助手从游戏的计算结果页读取可见的套装、二四六号位主属性和属性阈值，并把这些约束交给本地优化器。

优化输出分为三档：

- **可直接配装**：给出六件御魂、总属性、套装效果和替换顺序。
- **接近满足**：显示每个缺口及最小差距组合。
- **需要培养**：从未装备且未受保护的御魂中按预期收益/成本排序，生成 `+3` 检查点计划。

执行层只消费不可变的 `ActionPlan`。计划列出每一步目标御魂、本地指纹、预期页面、动作、置信度门槛和停止条件。任何实际属性与计划不一致都会废弃计划并要求重新扫描。

### 4. 日常任务

场景识别从“全屏 OCR 中是否出现某个词”升级为混合识别：

- 版本化的分辨率配置和感兴趣区域；
- 稳定按钮/标题的模板特征；
- OCR 文字作为语义确认；
- 页面指纹和动作后的画面变化作为复核。

困 28 首版仍只负责选怪、战斗、结算循环，不更换狗粮。御魂副本只从用户手动停留的挑战入口开始。每个动作前后都确认场景；未知场景保存证据包并停止。

## 桌面体验

“总览”改为任务导向：

- 连接与校准；
- 当前库存完整度和最近采集时间；
- 当前方案是否可满足；
- 日常任务入口与最近停止原因。

“御魂仓库”提供三个清晰入口：

1. 读取当前详情；
2. 导入 JSON 快照；
3. 引导式批量扫描（只有校准通过后可用）。

失败时展示具体阶段、识别到的文字摘要和诊断目录，不再只显示“读取失败”。所有写操作位于独立的“执行计划”页，默认只预览。

## 数据与兼容

- SQLite 继续作为本地事实来源；批量导入使用事务，任一不可恢复错误都不产生半份库存。
- 御魂记录增加 `source`、`source_id`、`captured_at` 和 `review_state`；旧记录迁移为 `manual_ocr` 来源。
- 同一来源的稳定 ID 用于更新；没有稳定 ID 的屏幕采集使用独立本地 ID，避免同属性御魂互相覆盖。
- JSON 适配器使用明确的格式探测和字段白名单，拒绝脚本、可执行文件和未知嵌套对象。

## 分阶段交付

### A. 可诊断的真实读取

修复详情解析器的错误锚点；保存截图/OCR 证据包；UI 展示失败阶段；未知场景保存现场。该阶段不新增游戏点击。

### B. 全量库存与本地决策

加入 JSON 导入、导入预览、事务写库、库存完整度与重复项处理；配装和强化建议只消费已确认记录。

### C. 引导式批量扫描

使用用户机器上生成的证据包建立 MuMu 分辨率配置，自动遍历御魂卡片并只读采集。扫描任务支持暂停、续扫和去重。

### D. 经确认的执行计划

实现锁定、弃置、`+3` 强化和穿戴计划。先以逐步确认模式交付；只有真实回放测试覆盖后才允许整批执行。

### E. 稳定日常循环

为困 28 和御魂副本分别建立场景夹具、混合识别器、动作后复核和恢复策略。首轮在 3 次以内验证，通过后用户再提高上限。

## 验收标准

- 详情页不含固定标题时，只要套装、等级和属性空间关系成立即可成功解析。
- 任意读取失败都能指出失败层，并在本地留下可复现的截图和 OCR JSON。
- 导入支持的 JSON 后，新增/更新/跳过/错误数量与文件内容一致；错误不会写入半份数据。
- 所有配装和强化结果来自真实、已确认库存；没有真实库存时明确阻止计算。
- 任何写操作执行前都有预览，受保护御魂不可能进入动作计划。
- 日常任务的未知页面不会产生点击，并保存最后现场。
- 全量单元测试、编译检查、依赖检查和 Git 空白检查通过。
